# Backend account deletion — coverage and recovery boundaries

October 1, 2026. Source review and isolated synthetic evidence only. This backend change is isolated from accepted local commit `53c1d25` onto main at `4d9356c`. The separate default-off WordPress resource commit `d76cfb4` is preserved locally and excluded from this PR. No live database, account, Storage, Redis, mail, payment or other provider call was made. Public Supabase documentation/source was read. No secrets or environment files were read during tests.

## Bounded correction implemented

The Auth helper previously accepted **every HTTP 404** as successful deletion, including an HTML gateway/route error. That made the endpoint return `ok: true` after database commit without evidence that the Auth account was absent. It also forwarded provider exception text and response bodies to native clients.

`app/routers/profile.py` now accepts an absent-user response only when HTTP 404 carries the exact machine code `error_code: user_not_found`. Unidentified/malformed 404s and other failures remain HTTP 502. The client receives one fixed message explaining that completion is unconfirmed and some data may already be removed. Server warnings contain only a fixed category or numeric HTTP status. Transport exception chaining is suppressed; there is no internal retry. Existing HTTP 200/204 acknowledgements and the successful native envelope (`ok`, `deleted_user_id`, `rows_deleted`, `tables_touched`) remain unchanged.

The focused suite reproduced 17 failed assertions on the old source (eight test methods, including subcases); all eight methods pass after the patch. It checks explicit absent-user handling, unknown 404 shapes, provider/transport redaction, no automatic retry, commit ordering, another user's preservation, scan exclusions and native response compatibility. This proves the bounded correction, not complete deletion coverage. Both native clients use the shared endpoint; Android treats 502 as unconfirmed and iOS throws its existing server error. No native UI or website parity change is needed for this response-contract-preserving correction.

## Exact source coverage rule

`_list_user_scoped_tables` discovers **catalog-visible BASE TABLEs** with a column named exactly `user_id` in `raw`, `app`, `content`, `marts` and `gaia`. `_delete_user_scoped_rows` removes matching subject rows, then separately deletes `gaia.users.id` if that column exists. The same discovery drives preflight counts. A configured URL/key makes `delete_ready` true; preflight does not prove Auth reachability, project/key alignment, key privilege, Storage eligibility, full coverage or process readiness.

The following inventory contains 29 migration-declared `user_id` tables, the one explicit `gaia.users` special case, five additional tables expected by runtime writers, and one context-only DDL table. **These 36 relations are a source map, not a verified production catalog.** Role visibility, installed migrations, actual relation types, constraints and privileges must be qualified separately. Dynamic discovery may include additional visible tables not declared here and may silently omit inaccessible or differently keyed relations. Only rows whose owner key matches the authenticated subject are explicitly targeted. Indirect FK cascades are not included in reported direct row counts, and historical cross-owner FK consistency is unverified.

## Partial failure and concurrency behavior

| Boundary | Current observable behavior | Remaining consequence |
| --- | --- | --- |
| Row deletion fails before commit | Auth is not called; the DB dependency attempts rollback. | Do not infer complete removal. A connection/commit failure can have uncertain durability. |
| Commit succeeds, Auth fails / response is lost | Row deletion is durable; HTTP error cannot undo it. New patch reports unconfirmed and redacts provider details. | No durable phase record, completion receipt or worker reconciliation exists. Requester may have an empty-but-authenticatable account. |
| Auth already absent | Only an explicit HTTP 404 `user_not_found` now counts as an absent-user acknowledgement. | A valid retry token can reconfirm this limited state; expired/removed credentials cannot recover an acknowledgement through the current route. Older/unknown 404 formats require reconciliation, not a success guess. |
| Both DELETE calls overlap | No shared deletion lease/receipt. Row operations may serialize incidentally; recognized absent-user acknowledgement permits repeat completion. | Does not fence normal requests, already-admitted writes, queued jobs or other devices. |
| Writer arrives after a table was swept / after commit | No account lifecycle barrier or final all-store verification. | Data can remain or be recreated even though the endpoint returns `ok: true`. An isolated fixture reproduced this schedule with one late synthetic symptom row. This is a model, not a live Postgres race test. |
| Auth deletion succeeds but old JWT is used | `decode_supabase_token` does not check live user/session existence or deletion state. RLS owner predicates alone likewise do not prove a current account. | Access-token expiry bounds ordinary JWT validity, not queued worker or webhook work. Synthetic token decoding after the mocked Auth acknowledgement remains successful. |

The successful response currently means **the discovered row statements committed and the Auth helper received an accepted acknowledgement**. It does not mean every associated store is empty, all access has stopped, every device is cleared, or providers/backups have erased all copies. The narrow patch intentionally does not upgrade that meaning.

## Minimal coordinated follow-up proposal (not implemented)

The concurrency fix spans admission, DB writes, queues, caches and provider reconciliation. An endpoint-only lock or reversing the two deletion steps is insufficient; keeping a DB transaction open during the Auth HTTP call would add failure/locking risk and still would not include all writers.

1. Add a durable account lifecycle/deletion-operation record in an application-owned schema, explicitly excluded from ordinary user-data deletion. Store only the account key, operation/version, phase and minimum error/status evidence; adopt its retention instead of silently retaining identifiers forever. Persist an authenticated, confirmed deletion intent before removing data.
2. Establish a **transactional write barrier**: every personal write, including an already-admitted request, direct/RLS write path, backlog drain, scheduled worker and billing webhook, must check the lifecycle at its commit boundary and coordinate with the deletion transition. A request-start check alone leaves a race. Use transaction-scoped coordination compatible with the configured pool; do not rely on process locks or session locks across pooled transactions. Reads/caches must deny a deleting/deleted account even when a JWT is cryptographically valid.
3. Once admitted writers finish and new ones are fenced, process idempotent phases with a durable lease/receipt: scoped rows, stored derived projections, queues/caches, Storage/provider work, then Auth confirmation and final coverage checks. Keep external calls outside long DB transactions. A retry resumes the recorded phase and a timeout remains uncertain until reconciled. Do not declare completion while an unresolved mandatory phase remains.
4. Use an explicit reviewed coverage manifest with required/optional installation rules and child/parent order, plus a fail-closed catalog comparison, instead of assuming the current visible `user_id` scan is exhaustive. Resolve the public billing/retention classification before adding deletion rules. Hosted qualification later needs a dedicated synthetic account/environment and permission to exercise its stores.

The smallest reviewable next implementation brief is the lifecycle/write-barrier contract and an enumerated writer inventory; then a bounded synthetic two-writer test for in-flight write vs deletion, queued replay, stale webhook, cached read, duplicate request, Auth timeout and expired-token receipt recovery. This is a technical coordination requirement, not a reason to halt unrelated product or growth work. No new owner question is issued here.
